Long-read RNA-seq MVP：服务器补充与真实 FASTQ→counts 流程实施方案

日期：2026-10-06

适用项目：bulk-rnaseq-governance-mvp

一句话结论：目前 long-read 已完成的是“本地代码结构接入”和“治理框架骨架”，不能默认服务器已经完成。服务器需要先同步这些代码；随后还要继续开发并验证真正的 ONT FASTQ → minimap2 → samtools → featureCounts → gene_counts_raw.tsv 执行流程。

0. 先用通俗语言理解这件事

你现在做的平台可以分成两层：

层次 通俗理解 在本项目里对应什么
治理层 像医院检验科的信息系统：登记样本、记录是谁的数据、文件在哪里、用了哪个参考标准、结果是否合格。 dataset 定义、samplesheet、manifest、checksum、状态管理、validation report、provenance。
分析层 像真正做检测的仪器和实验流程：把原始 FASTQ 数据加工成 counts。 minimap2 比对、samtools 处理 BAM、featureCounts 计数、QC 统计。

目前已经完成的是第一层的一部分：系统已经知道“long-read 是一类独立数据，不能走 Illumina short-read 的 STAR/Salmon 路线”。但第二层——真正把 long-read FASTQ 跑成 counts 的工具链——还没接上。

为什么要分两层？
因为平台未来会同时管理 short-read、rRNA depletion、long-read、公共数据库数据和用户上传数据。如果不先把“治理层”设计清楚，后面不同数据类型的结果会混乱：不知道哪个 counts 是用什么方法产生的，也不知道能不能放在一起分析。

0.1 几个核心概念先解释清楚

概念 是什么意思 为什么重要
FASTQ 测序仪或公共数据库给出的原始序列文件，里面包含 reads 序列和每个碱基的质量值。 它是从原始测序数据开始统一处理的入口。要想统一分析公共数据，最好从 FASTQ 开始。
counts 每个基因在每个样本里被多少 reads 支持的计数表。 它是后续差异表达、聚类、通路分析等研究最常用的基础表达矩阵。
比对 alignment 把 FASTQ 里的 reads 放回参考基因组上，看每条 read 来自哪个基因组位置。 不知道 read 来自哪里，就无法判断它应该计入哪个基因。
minimap2 常用的长读长比对工具，适合 Nanopore/PacBio 这类 long-read 数据。 STAR 更适合 Illumina short-read；long-read 需要适合长 reads 的比对工具。
BAM 比对结果文件，记录每条 read 比到了哪里。 featureCounts 等计数工具通常从 BAM 中判断 reads 属于哪个基因。
samtools 处理 BAM 文件的常用工具，可以排序、索引、统计比对情况。 很多下游工具要求 BAM 已排序和索引；同时它能生成 alignment QC。
featureCounts 根据 GTF 注释文件，把比对到基因区域的 reads 计入相应基因。 它负责把“每条 read 在哪里”转换成“每个基因有多少 reads”。
GTF 基因注释文件，告诉工具哪些基因在基因组的什么位置。 没有 GTF，就无法把 reads 归属到标准基因 ID。
provenance 结果来源记录：用了什么输入、什么参考、什么软件、什么参数、什么版本。 科研结果需要可追溯，否则别人无法复现，也无法判断不同数据能否整合。

2. 服务器如何补充已完成的本地代码结构

这一阶段的目的：把本地已经写好的 long-read 治理框架代码同步到服务器。

为什么要做：真正运行分析是在服务器上完成的。如果服务器代码还是旧版本，它根本不知道什么是 human_longread_rnaseq_v1，也不会生成 long-read samplesheet，更不会分流到 long-read 执行器。

如果不做会怎样：你在服务器上运行时，最多只能使用之前的 short-read MVP；long-read 相关命令、定义和文件都不存在。

3. 如何补充真实 FASTQ→counts 流程

真实流程要补的是 rnaseq-mvp-longread 背后的执行器。建议第一版先做 ONT FASTQ 到 gene-level counts。

为什么不是继续改原来的 short-read 流程：原来的流程是 STAR + Salmon + tximport，主要为 Illumina short-read RNA-seq 设计。Nanopore long-read 的 read 更长、错误模式不同、数据结构不同，所以应该用 long-read 适配工具链。

3.1 第一版目标

ONT FASTQ
→ minimap2 splice-aware alignment
→ samtools sort/index
→ featureCounts gene assignment
→ gene_counts_raw.tsv
→ alignment_summary.tsv
→ longread_qc_metrics.tsv
→ provenance.json
→ validation_report.json

建议用 Docker/Apptainer 容器固定工具版本，避免服务器环境漂移。若先用系统包试跑，可安装：

为什么要固定工具版本：同一个 FASTQ，用不同版本的软件或不同参数，可能得到不完全一样的 counts。为了科研复现，必须记录并尽量固定版本。

阶段 C：执行流程

这一步做什么：真正把 FASTQ 变成 BAM，再把 BAM 变成 counts。

为什么要先 minimap2：FASTQ 只是 reads 序列，还不知道这些 reads 来自哪个基因。minimap2 的作用是把 reads 放回参考基因组。

为什么要 samtools sort/index：比对后的 BAM 需要整理成标准顺序，并建立索引，很多下游工具和 QC 工具才可以高效读取。

为什么要 featureCounts：比对只回答“read 在基因组哪里”，featureCounts 才回答“这条 read 应该算到哪个基因”。

# 1. 比对
minimap2 -ax splice -uf -k14 reference.fa sample.fastq.gz > sample.sam

# 2. 排序
samtools sort -@ 8 -o sample.sorted.bam sample.sam

# 3. 索引
samtools index sample.sorted.bam

# 4. BAM 统计
samtools flagstat sample.sorted.bam > sample.flagstat.txt

# 5. gene-level counts
featureCounts \
  -T 8 \
  -L \
  -t exon \
  -g gene_id \
  -a annotation.gtf \
  -o featurecounts.gene_counts.txt \
  sample.sorted.bam
注意：minimap2 -uf -k14 更适合 ONT direct RNA。对于 ONT cDNA，可能使用 -ax splice 即可。第一版需要根据 protocol 分别选择参数。

5. 测试与验收

为什么要先用 tiny 数据测试：完整 long-read 数据通常很大，第一次就跑真实数据会很慢，而且出错后很难定位。tiny FASTQ/FASTA/GTF 可以快速验证流程逻辑是否正确。

测试不是形式主义：这里的测试是为了回答三个问题：命令能不能生成？文件能不能产出？产出的 counts 格式是否符合治理标准？

5.3 服务器 smoke test

smoke test 是什么意思：不是正式科研分析，而是“冒烟测试”：确认整个流程能从头跑到尾，不会一启动就崩。

为什么服务器也要 smoke test：本地测试通过不代表服务器通过。服务器的软件、路径、权限、CPU 架构、容器环境都可能不同。

6. 推荐实施顺序

下面这个顺序的核心原则是：先让代码同步，再让小数据跑通，最后再上真实数据。不要跳步。

  1. 先把当前本地代码提交并部署到服务器。
  2. 服务器确认 long-read 骨架文件存在，测试通过。
  3. 本地继续开发 rnaseq-mvp longread-run 命令。
  4. 用 tiny FASTQ/FASTA/GTF 完成单元测试和集成测试。
  5. 服务器安装或容器化 minimap2/samtools/subread/seqkit。
  6. 服务器跑 smoke test。
  7. 再选择一个小型真实 ONT public FASTQ 做真实验证。
  8. 最后再考虑接入 GEO/SRA 公共目录和用户上传流程。

7. 不建议现在做的事

这些不是永远不能做，而是不适合第一版 MVP 做。第一版目标应该是“可控、可解释、可验收”。

  • 不要直接用完整公共 long-read 数据集做首次测试。
  • 不要把 long-read counts 和 short-read Salmon counts 直接合并做差异分析。
  • 不要同时支持 ONT、PacBio、isoform discovery、modification calling。
  • 不要让 LLM 判断 QC 是否通过，必须由确定性指标和阈值判断。
